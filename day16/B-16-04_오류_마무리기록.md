## 막힌 지점 → 해결 타임라인 (실증거 기반)

| # | 증상 | 원인 (증거) | 조치 |
|---|---|---|---|
| 1 | 취소 실행이 서버에서 실패 (HTTP 500) | v1 트리거에 `<SLACK_WEBHOOK_URL>` 잔존 — 오류가 취소 자체를 **롤백** (`invalid URL` 메시지) | 알림을 예외 격리(begin/exception) — **알림 실패가 업무를 막지 않게** (v2) |
| 2 | 취소는 되는데 슬랙 안 옴 + **접수 알림까지 중단** | v2도 플레이스홀더 그대로 실행 → 정상이던 접수 함수까지 덮어씀 (`placeholder_left=true` ×2) | URL을 함수에서 분리 — `app_settings` 설정 테이블 (v3) |
| 3 | v3 후에도 양쪽 다 안 옴 | 설정 값이 예시 문구 그대로 (`url_length=40`, Slack이 HTML 200 반환 — 발송 파이프라인은 정상 가동 증명) | **실행 가능한 완성 한 줄**(실제 URL 포함 UPDATE) 제공 → 즉시 해결 |

## 실행 확인 (최종)

접수 → ☕ 슬랙 / 취소 → 🚫 슬랙, 한 사이클 라이브 실증 (진짜최종 09:10, 사장 확인 10:30)

## 교훈 (이번 주의 알짜)

1. **사람이 치환해야 하는 값은 반드시 틀린다** — 3번 반복됐다. 해결은 주의가 아니라 구조: 설정을 코드에서 분리하고(설정 테이블), 전달은 실행 가능한 완성본으로.
2. **알림(부가 기능)의 실패가 업무(핵심 기능)를 죽이면 안 된다** — 트리거 안 예외 격리는 선택이 아니라 기본값.
3. **침묵하는 실패가 가장 비싸다** — 예외 격리의 대가는 조용한 실패. `net._http_response`와 설정 길이처럼 **비밀을 노출하지 않는 진단 쿼리**를 준비해 두면 침묵을 뚫을 수 있다.
4. 진단은 증거 순서대로: 함수 버전(placeholder 여부) → 트리거 존재 → 설정 값 길이 → 발송 기록. 감이 아니라 배제로 좁힌다.
