## 잘된 것

1. **기획 → 화면의 일관성**: Day 02에 정한 핵심 유저 스토리 ★("출근 전 미리 픽업 예약")가 그대로 Day 03 첫 화면이 됐고, Day 05에 PRD의 문제·타깃·가치가 화면 문구("줄 서는 5분, 예약하면 0분")로 반영됨 — 문서가 장식이 아니라 실제 기준으로 작동.
2. **검증 체계 정착**: "구현 → Playwright 자동 검사" 흐름을 규칙화 — 매 변경마다 로컬·배포 URL에서 19항목 실측. 감이 아니라 근거로 완료를 판정.
3. **다면조사 활용**: 투자자·CTO·허가기관·고객 4관점 검토가 실제 기능이 됨 — 개인정보 동의(허가기관), 슬롯 상한·재고 문구(CTO·투자자), 픽업 정확도 중시(고객)가 전부 화면에 반영.
4. **배포 파이프라인**: GitHub(공개 저장소) + Vercel 연결로 `git push` = 재배포. 수정→검증→배포 사이클이 분 단위로 단축.
5. **커리큘럼보다 앞선 진행**: 통합(Day 05 주제)을 Day 03~04에 이미 수행 — Day 05는 메시지 다듬기에 집중할 수 있었음.

## 배운 것

- **localStorage의 성격과 한계**: 새로고침에도 남지만 "그 브라우저 안"에만 존재 — 고객 폰의 예약이 사장에게 도달하지 않는다. 진짜 수집은 서버(Day 11 Supabase)가 필요. 데모와 실서비스의 경계를 명확히 인지.
- **네이티브 UI의 재발견**: 커스텀 셀렉트 없이도 `option disabled`+라벨로 "예약 마감 (n/3)"을 구현 — 표준 기능 확인이 먼저, 커스텀은 그다음.
- **되돌릴 수 없는 것의 무게**: GitHub 저장소 생성 이슈를 계기로 "외부 리소스는 실행 직전 단독 확인, 삭제는 직접" 원칙 수립.
- **역할 분리 설계**: 예약 목록을 관리자 화면으로 분리하며 "누가 무엇을 봐야 하는가"를 처음 고민 — 개인정보 관점이 UI 구조를 바꿈.

## 아쉬운 것 · 남은 리스크

- **수요는 여전히 가설**: "출근길 직장인이 사전 픽업을 원한다"는 실측되지 않음 (R1 Q4 검증 항목 그대로). 화면은 완성됐지만 시장 검증은 시작 전.
- **주문이 사장에게 안 모임**: localStorage 한계로 실제 접수 불가 — Day 11(Supabase)에서 해결 예정.
- **디자인 정리(통합 3단계)는 최소만**: 기능·메시지 통합에 집중, 세밀한 디자인 다듬기는 방과후 과제로 이월.
- 캡처에 실명 데이터를 쓴 실수 1회 — 이후 가짜 데이터 원칙 준수.
