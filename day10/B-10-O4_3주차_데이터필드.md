# B-10-O4 — 3주차 데이터 필드 초안 (Supabase 대비)

> 관리번호: **B-10-O4** (기초반 · 10일차 · 산출물 4) · 작성일: 2026-07-17
> 목적: Day 11(Supabase)에서 localStorage → 서버 DB로 옮길 때 쓸 필드 정의 — **이미 검증된 확정 JSON 구조(Day 04)를 그대로 승계**

## bookings 테이블 초안

| 필드 | 타입(초안) | 제약 | 유래 (localStorage 확정 구조) |
|---|---|---|---|
| id | uuid (기본키) | default gen_random_uuid() | `bk_타임스탬프` → 서버 표준 uuid로 승격 |
| name | text | not null | 동일 |
| phone | text | not null — **숫자만 11자리** | 동일 (표시 포맷은 클라이언트) |
| menu | text | not null | 동일 |
| qty | int2 | 1~3 check | 동일 (슬롯 정책) |
| pickup_date | date | not null | pickupDate |
| pickup_time | text('HH:MM') | not null | time |
| note | text | nullable | 동일 |
| status | text | check: 접수/확정/픽업완료/취소, default '접수' | 동일 |
| created_at | timestamptz | default now() | createdAt |
| consent_at | timestamptz | not null | consentAt (동의 증빙) |
| updated_at | timestamptz | default now() | updatedAt |

## 규칙 승계 (서버에서도 유지할 것)

- 슬롯 상한: 같은 pickup_date+pickup_time의 qty 합(접수·확정만) ≤ 3 — 서버 검증 필요(동시 요청 대비)
- 개인정보: 수집 최소(이름·전화), 보유 1개월 후 파기 → **파기 배치/정책 필요** (서버로 가면 진짜 의무가 됨)
- 상태 전이: 접수→확정→픽업완료 / 접수↔취소, 확정 이후 삭제 잠금

## 3주차에 새로 잴 것(리드·측정 대비 메모)

- 예약 전환 퍼널: 페이지 방문 → 폼 시작 → 제출 → 픽업완료 (Umami, Day 14)
- 노쇼율: status가 픽업 시간 경과 후에도 확정에 머문 비율
- 재방문: 동일 phone 해시 기준 반복 예약 (개인정보 최소화 — 해시 검토)
