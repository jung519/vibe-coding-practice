# B-13-03 — 관리 화면 접근 보호

> 관리번호: **B-13-03** (기초반 · 13일차) · 작성일: 2026-07-22
> 방식: **Supabase Auth 로그인 (A안)** — 화면 비밀번호(프론트 장식)가 아닌 서버 인증

## 보호 계층 (무엇이 무엇을 막는가)

| 계층 | 설정 | 막는 것 |
|---|---|---|
| 1. 가입 차단 | Authentication → "Allow new users to sign up" **OFF** | 아무나 계정을 만들어 `authenticated`가 되는 것 — **A안의 전제** |
| 2. 사장 계정 1개 | Users → Add user (이메일+비밀번호) | 로그인 주체를 사장으로 한정 |
| 3. RLS 정책 | `authenticated`에만 SELECT·UPDATE (`day13/setup.sql`) | 익명 키로 개인정보 조회 — URL·페이지 코드를 알아도 데이터는 안 나옴 |
| 4. 컬럼 제한 | UPDATE는 `status`·`updated_at`만 grant | 로그인 상태에서도 이름·전화·예약 내용 변조 불가 |
| 5. DELETE 정책 없음 | (의도) | 화면·API를 통한 삭제 — 파기는 Table Editor에서만 |
| 6. noindex + 세션 저장소 | `meta robots` · sessionStorage(탭 닫으면 로그아웃) | 검색 노출·공용 PC 세션 잔류 |

## 왜 "화면 비밀번호"로 안 했나 (교재 기본형과의 편차 근거)

교재 기본형(anon SELECT 정책 + 화면 접근 보호)은 화면만 잠그고 **데이터는 열어둔다** — 익명 키는 페이지 소스에 공개돼 있으므로, 화면을 거치지 않고 API를 직접 호출하면 예약자 전원의 이름·전화가 노출된다. Day 11에 세운 원칙("테이블은 잠그고 정해진 창구만")과 충돌하여 **서버 인증(A안)으로 결정** (사장 판정, 2026-07-22).

## 검증 (tests/day13-check.js — 9항목)

- 비로그인·오입력 시 게이트 차단, 데이터 미노출 (A1·A2)
- JWT 조회·상태 변경, PATCH는 `status`·`updated_at`만 전송 (A3~A5)
- 삭제 버튼 없음 (A6) · **토큰 만료 → 자동 갱신 → 재시도** (A7 — 이 테스트가 갱신 토큰이 덮이는 실버그를 잡음)
- 로그아웃 세션 제거 (A8) · 375px·noindex (A9)

## 남은 한계 (정직하게)

- 비밀번호 유출 시 그대로 뚫림 — 2FA 없음 (Supabase Auth MFA는 추후 과제)
- 사장 계정 비밀번호 관리 책임은 운영자에게 (재설정: 대시보드 → Users)
